# Gemma Cross-Dataset Boundary Validation Design

## Goal

Evaluate local-evidence machine-generated-text (MGT) classifiers derived from
existing Gemma 3 1B Instruct processing outputs. Compare separate source-dataset
classifiers with a mixed-data classifier, measure cross-dataset classification,
and validate boundary predictions on the currently processed SemEval subset.

## Scope

The experiment uses only paired Stage 1 logprob and Stage 2 token-similarity
artifacts already available under `TEXT_DETECTION_DATA/processed`. It does not
run language-model processing or write new local-evidence window Parquet caches.

Binary training and evaluation sources are:

- `kaggle_train`
- `mage_train`
- `outfox_chatgpt_train`

`custom_2025` is excluded so cross-dataset results remain comparable across the
three established training sources. HG-only datasets are excluded because they
cannot train or evaluate binary MGT classification.

## Data Preparation

Build local-evidence windows in memory with the established configuration:

- model: `gemma_3_1b_it`
- window lengths: 32, 64, and 128 tokens
- stride: 16 tokens
- top-k candidates: 20

Each source dataset supplies HG and MG windows. The mixed cohort concatenates
all three sources and qualifies each parent text identity with its source dataset
before partitioning, preventing identical split/text IDs from crossing train and
test partitions.

Before use, verify that each split has matching Stage 1 and Stage 2 records.
Incomplete cohorts are excluded with an explicit coverage report rather than
silently included.

## Models And Classification Evaluation

Fit logistic-regression local-evidence classifiers for four regimes:

- Kaggle-only
- MAGE-only
- Outfox-only
- mixed Kaggle, MAGE, and Outfox

Use the established fixed seed of 42 and existing local-evidence fitting and
scoring utilities. For every regime, report held-out in-domain performance and
transfer performance against every other compatible source dataset. Report
text-level macro-F1 after the existing window-to-text aggregation.

Persist fitted classifiers through the existing model cache. Cache keys must
continue to distinguish model alias, window length, feature schema, training
data, and training configuration.

## SemEval Boundary Validation

Score the SemEval 2024 Task 8 Subtask C dev windows generated by
`gemma_3_1b_it`. Evaluate only the paired, currently processed subset of 270
MG texts (`id` 0 through 269), and label all resulting tables as partial
coverage: `270/505` texts.

For each trained regime and window length, predict token boundaries using:

- MG threshold: 0.5
- smoothing window: 5 tokens
- sustained crossing length: 3 tokens

Align predictions with SemEval annotations through the existing boundary
utilities. If token labels cannot reconstruct an annotated text, exclude that
text from boundary aggregates and list its ID and reason. Report the valid-text
count, mean absolute token error, exact-boundary accuracy, and within-5-token
accuracy.

## Notebook And Verification

Create a dedicated notebook for this Gemma experiment. It must:

- load only existing processed artifacts;
- show source coverage before fitting;
- present cross-dataset macro-F1 and SemEval boundary tables;
- distinguish unsupported, incomplete, and excluded cohorts;
- avoid stored execution outputs when committed.

Add a focused notebook contract test that verifies the Gemma alias, three source
datasets, partial SemEval configuration, required result tables, and no pipeline
processing calls. Execute a non-interactive smoke run against the current data,
then run the affected pytest tests.

## Non-Goals

- Fine-tuning Gemma 3 1B Instruct.
- Processing additional SemEval texts.
- Processing Phi-4 Mini Reasoning data.
- Training on or evaluating `custom_2025` or HG-only datasets.
